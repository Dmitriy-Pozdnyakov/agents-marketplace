# Работа со спецификацией API поставщика для IDP

Репозиторий ведёт команда, которая разрабатывает и предоставляет AI-агентов, базы знаний и RAG-сервисы. Спецификацию читают инженеры действующей корпоративной IDP. По ней они должны суметь настроить карточку продукта, отправить заказ и показать сотруднику готовый ресурс или причину ошибки.

## Перед изменением

- Начни со сценария сотрудника и действия клиента API. Укажи, что именно изменится для сотрудника, команды IDP или поставщика.
- Прочитай [предложение по интеграции](README.md) и затронутую операцию в [OpenAPI](openapi.yaml). В Git-репозитории проверь ветку и рабочее дерево, сохрани чужие правки.
- Отличай сведения владельца IDP от наших предложений. Правило действующей платформы подкрепляй ссылкой на её контракт или решением команды. Для открытого вопроса укажи предлагаемое значение и на что повлияет ответ.

## Границы ответственности

- Для каждой операции называй инициатора, исполнителя и владельца результата. Пример основного пути — IDP отправляет заказ, поставщик создаёт экземпляр, IDP открывает сотруднику доступную точку входа.
- Различай карточку с версией шаблона, заказ в проекте и созданный ресурс. Один шаблон можно заказать несколько раз. Повтор отправки одного заказа должен вести к одному экземпляру.
- Описывай создание ресурса и его дальнейшее использование как отдельные сценарии. Для агента это могут быть создание и первый диалог, для базы знаний — выдача и загрузка документов, для RAG-сервиса — создание и первый запрос по выбранным базам.
- Внутреннее устройство модели, индексатора или хранилища включай в контракт, когда оно влияет на выбор сотрудника, права, готовность или наблюдаемую ошибку.

## Как менять контракт

- Поля, обязательность, допустимые значения, заголовки, коды HTTP и примеры поддерживай в OpenAPI. В README описывай решения, которые предстоит принять интегратору, и критерии приёмки.
- Для каждого входного параметра обозначай источник. Различай выбор сотрудника, контекст проекта в IDP и настройку, заданную поставщиком в шаблоне.
- Для асинхронной операции задай порядок состояний и значение «готов» для конкретного продукта. Опиши поведение при двойном нажатии, потере ответа, закрытии страницы и ошибке выдачи.
- Для ссылок на базы знаний опиши проверку доступа проекта. В примерах используй вымышленные идентификаторы, адреса и данные. Секреты передавай через согласованный механизм аутентификации.
- При изменении существующего поля или статуса проверь влияние на клиент IDP и незавершённые заказы. Для несовместимой правки опиши переход со старого контракта.

## Проверка и завершение

- Проверь синтаксис OpenAPI, внутренние ссылки и соответствие примеров схемам. Сверь названия статусов и кнопок в описании сценария с ответами API.
- Пройди затронутый сценарий глазами интегратора. Например, после тайм-аута первого запроса клиент должен знать, как получить тот же заказ, а после успешного опроса — какую ссылку показать сотруднику.
- В ответе укажи изменённую операцию, результат проверки и решения, которые остаются за командами. При наличии реализации отдельно укажи, какие сценарии проверены на стенде.
