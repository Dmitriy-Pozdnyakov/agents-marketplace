# Пример GitLab-репозитория SRE-агента для Grafana

Дежурный в проекте `team-checkout` выбирает Grafana, правило `checkout-5xx` и канал `rca-checkout`. По кнопке **«Подключить» IDP сама создаёт подключение и устанавливает адаптер в свой Kubernetes**. Когда приходит алерт, адаптер передаёт его действующему SRE-исследователю и доставляет отчёт в выбранный канал.

Это образец **поставки** для двух команд. В репозитории есть исполняемый пример преобразования webhook, описание релиза, конфигурация проекта и манифесты. Адреса, SHA и digest вымышлены. Для стендовой установки команда агентов публикует настоящий образ с HTTP-адаптером и программой сквозной проверки. Пример преобразования можно запустить отдельно на Python 3.11+.

## Что открыть на встрече

| Файл | Кто использует и зачем |
| --- | --- |
| [marketplace/offering.yaml](marketplace/offering.yaml) | IDP читает название карточки, владельца, `parameterSchema`, версию, точный образ и относительные пути к манифестам. Так определяется, **что показать** и **что установить**. |
| [.env.example](.env.example) | Команда агентов описывает настройки образа. IDP использует этот перечень для настройки среды. Адреса берутся из ConfigMap, значения пяти токенов — из хранилища секретов проекта. |
| [example-inputs/connection.yaml](example-inputs/connection.yaml) | Пример результата заполнения формы. Сервер IDP записывает его в ConfigMap как файл подключения. |
| [deploy/kubernetes/grafana-rca-adapter.yaml](deploy/kubernetes/grafana-rca-adapter.yaml) | Исполнитель IDP применяет **Deployment и Service**. Контейнер получает настройки через env и смонтированный файл. |
| [deploy/tests/rca-smoke-job.yaml](deploy/tests/rca-smoke-job.yaml) | После запуска адаптера IDP применяет **Job** из того же релиза. Он определяет, когда можно показывать «Подключено». |
| [src/adapter.py](src/adapter.py) | Компонент команды агентов. На синтетическом webhook показывает, какое тело получит `POST /v1/investigations`. |

## Что вводит дежурный и что предоставляет среда

Форма содержит **три** поля — `grafanaConnectionId`, `ruleUids`, `deliveryChannelId`. IDP фильтрует варианты по проекту и проверяет выбор дежурного при отправке. Список правил зависит от выбранной Grafana. К ним IDP добавляет `projectId` из сессии и свой стабильный `connectionId`. При повторе исходного действия используются тот же ID и то же размещение. В примере пять значений хранятся в `connection.yaml`. Файл записан в JSON-синтаксисе YAML, чтобы его также мог прочитать локальный пример без дополнительных библиотек.

**Для экземпляра.** В ConfigMap `rca-conn-checkout-01-config` лежат `connection.yaml`, базовый адрес исследователя `RCA_API_BASE_URL` и адрес предлагаемого реестра проектных подключений `PROFILE_API_BASE_URL`. По доверенному профилю правила адаптер получает целевой сервис, UID трёх источников и ссылку на логи. В Secret `rca-conn-checkout-01-secrets` IDP предоставляет `RCA_API_TOKEN`, `PROFILE_API_TOKEN`, `GRAFANA_WEBHOOK_TOKEN` и `DELIVERY_API_TOKEN`. Контейнер слушает порт `8080` и читает файл по пути `/etc/adapter/connection.yaml`.

**Только для проверки.** В том же ConfigMap заданы тестовый источник `SMOKE_FIXTURE_ID` и стабильный ID проверки `SMOKE_RUN_ID`. Учётные данные `SMOKE_TRIGGER_TOKEN` получает только Job из Secret. Тестовый источник, реестр профилей и техническую возможность проверить доставку в выбранный канал нужно согласовать с их владельцами. Значения секретов в GitLab не хранятся.

## Что делает IDP по кнопке

1. **Фиксирует заказ.** Сохраняет выбранный релиз, параметры формы, ID подключения и разрешённый namespace. В примере имя ресурсов — `rca-conn-checkout-01`. Для другого подключения IDP подставляет его уникальное имя в имена ресурсов, селекторы и ссылки на ConfigMap и Secret. Повтор одного заказа продолжает ту же установку.
2. **Готовит среду и применяет манифест.** Создаёт ConfigMap и привязывает проектные секреты. Исполнитель берёт манифест из коммита, указанного в offering, а Kubernetes скачивает готовый образ по digest. Service даёт внутренний адрес `rca-conn-checkout-01:8080`. IDP обеспечивает доступ Grafana к аутентифицированному webhook и внутренний маршрут с SSO к странице `/connections/conn-checkout-01`.
3. **Проверяет весь путь.** Когда Deployment готов, IDP запускает поставленный Job. В настоящем образе `/app/bin/rca-smoke` инициирует синтетический HTTP 5xx для выбранного правила, сверяет завершённое расследование и квитанцию доставки для этого подключения. При успехе возвращает код 0. IDP показывает «Подключено» и ссылку на страницу. Если маршрут не настроен или доставка не подтверждена, IDP показывает шаг сбоя. Готовность процесса по `/readyz` — только промежуточная проверка.
4. **Обрабатывает повторы проверки.** Повтор установки с тем же `SMOKE_RUN_ID` должен найти ту же попытку и тот же Job. Для осознанно новой проверки IDP назначает новое имя Job и новый ID запуска. Квитанция подтверждает именно тест этой попытки. Состояние заказа и ссылка на подключение ведутся в IDP. Вызовы API заказов поставщика для этого пути не требуются.

### Какие объекты получит Kubernetes

Из корня этого примера можно вывести ConfigMap без передачи значений секретов. В боевой среде IDP подставит согласованные адреса и согласованное окружение проекта.

```bash
kubectl -n team-checkout create configmap rca-conn-checkout-01-config \
  --from-file=connection.yaml=example-inputs/connection.yaml \
  --from-literal=RCA_API_BASE_URL=https://rca.example.invalid \
  --from-literal=PROFILE_API_BASE_URL=https://profiles.example.invalid \
  --from-literal=SMOKE_FIXTURE_ID=checkout-test-5xx \
  --from-literal=SMOKE_RUN_ID=conn-checkout-01-smoke-1 \
  --dry-run=client -o yaml
```

С подготовленным тестовым кластером исполнитель может проверить манифесты через API Kubernetes в режиме проверки.

```bash
kubectl -n team-checkout apply --dry-run=server -f deploy/kubernetes/grafana-rca-adapter.yaml
kubectl -n team-checkout apply --dry-run=server -f deploy/tests/rca-smoke-job.yaml
```

Для настоящей установки сначала нужны существующий namespace и полномочия исполнителя, доступный образ, ConfigMap, Secret и работающие проектные интеграции. Исполнитель применяет Deployment и Service, ждёт готовности Deployment, затем создаёт Job и читает условие `Complete` или `Failed`. Результат выдачи подтверждается тестом с доставкой через реальную Grafana и выбранный канал.

## Попробовать преобразование алерта локально

Команда использует [профиль тестового правила](example-inputs/profile.json) и [входящий webhook](example-inputs/webhook.json). Она печатает подготовленное тело расследования в stdout. Сетевые запросы не выполняются.

```bash
python3 src/adapter.py \
  --connection example-inputs/connection.yaml \
  --profile example-inputs/profile.json < example-inputs/webhook.json
```

Ожидаемый результат — один элемент в `investigations`, сервис `checkout`, `alert.labels.code` равен `"503"`, а `rejected` пуст. При повторе того же файла `request_id` сохраняется. Полный HTTP-приёмник, проверка полномочий внешних сервисов, устойчивое хранение, доставка, UI и тестовый бинарник входят в реализацию настоящего релиза. Пакет демонстрирует их контракт и границу ответственности.
