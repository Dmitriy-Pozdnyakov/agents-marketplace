# Чат-агент для поручений в GitLab

Предлагаемый продукт для корпоративного каталога IDP. Реализация и стенд для этого примера отсутствуют. Сотрудник открывает чат в своём проекте и пишет «Создай задачу „Проверить вход после обновления“ с описанием „Проверить вход тестовой учётной записью на стенде“». Результат поручения — созданная в выбранном проекте GitLab задача (issue). В диалоге сотрудник получает её номер и ссылку.

## Карточка, заказ и запуск

Поставщик публикует в GitLab версию `chat-task-agent-v1` типа `agent` с описанием возможностей, схемой формы, идентификатором коммита, путём к манифесту Kubernetes и образом агента, закреплённым по digest. Репозиторий релиза содержит код агента. Проект GitLab, где агенту предстоит создавать задачи, выбирает сотрудник при заказе. [Пример описания релиза](../examples/chat-task-agent-offering.yaml)

| Поле формы | Как IDP заполняет список |
| --- | --- |
| `gitlabConnectionId` | Зарегистрированные подключения GitLab, разрешённые сотруднику в текущем проекте IDP. Выбранное значение — строковый ID подключения. |
| `targetRepositoryId` | Зарегистрированные проекты GitLab, доступные через выбранное подключение и разрешённые проекту IDP. Значение — строковый ID целевого репозитория. |

Сервер IDP определяет проект и пользователя по сессии. По кнопке «Создать агента» сохраняет свой заказ, версию и выбранные параметры. До деплоя проверяет, что сотрудник вправе использовать оба ресурса и целевой репозиторий относится к указанному подключению. При повторе исходного действия IDP продолжает работу с прежним экземпляром. Пример конфигурации для исполнителя IDP приведён ниже.

```json
{
  "projectId": "team-checkout",
  "offeringId": "chat-task-agent-v1",
  "parameters": {
    "gitlabConnectionId": "gitlab-demo",
    "targetRepositoryId": "repo-demo"
  }
}
```

По предлагаемой схеме IDP автоматически развёртывает экземпляр в Kubernetes. Конфигурацию среды и ссылки на секреты предоставляет платформа. В параметрах заказа достаточно идентификаторов подключения и репозитория. Текст поручения сотрудник вводит в чате после выдачи экземпляра. Поставщик отвечает за образ агента и работу инструмента GitLab, IDP — за размещение экземпляра и доступ к нему. [Сценарий интеграции](../README.md)

Пока чат или инструмент запускается, IDP показывает «Создаётся». Исполнитель IDP проверяет вход в чат, ответ на контрольное сообщение и доступность инструмента для разрешённого репозитория. При успешной проверке IDP показывает «Открыть агента» и адрес экземпляра. При окончательном отказе сохраняет причину и номер собственного заказа.

## Исполнение поручения

Агент извлекает из сообщения заголовок и описание. Если заголовок неясен, уточняет его в диалоге. Перед записью агент проверяет текущие права вошедшего сотрудника, разрешение проекта IDP использовать подключение и право создавать задачи в выбранном репозитории. Текст сообщения не меняет область выданного доступа. При отказе агент сообщает причину в чате. Состояние завершённого заказа экземпляра сохраняется.

Для каждого поручения агент до вызова GitLab сохраняет идентификатор действия, стабильный идентификатор сообщения в этом чате, целевой проект и данные задачи. Повторная доставка сообщения использует ту же запись. Параллельную отправку одного действия блокирует агент. В описание задачи он включает уникальную метку поручения для сверки. Получив подтверждение GitLab, агент сохраняет номер и ссылку. Если оборвалась только доставка ответа в чат, сотрудник получает сохранённый результат. [Создание issue в GitLab](https://docs.gitlab.com/api/issues/#create-an-issue)

Если ответ потерян между GitLab и агентом, в чате отображается «Уточняется результат». Агент сверяет метку и проект с записью в GitLab. Подтверждённая задача завершает поручение. Пока результат невозможно установить, агент сохраняет поручение для сверки оператором и воздерживается от повторной записи. Новый запрос на создание допустим после подтверждения, что прежний вызов не создал задачу.

**Приёмка.** Выдать экземпляр и открыть чат. Выполнить пример поручения, перейти по ссылке и сверить проект, заголовок и описание. При повторной доставке того же сообщения и потере ответа после записи проверить, что сотрудник получил ссылку на ту же задачу. После отзыва у сотрудника права записи следующее поручение должно завершиться отказом без создания issue.
